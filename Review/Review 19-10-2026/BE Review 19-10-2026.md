## Phần 1 — Thiết kế Auth Token (Access & Refresh)

### Tại sao không dùng tokenVersion nữa?

`tokenVersion` là một số trên bảng `users`. Mỗi khi user đăng xuất, số này tăng lên 1. Middleware sẽ từ chối mọi access token có `tokenVersion` cũ hơn trong DB.

**Vấn đề:** Nếu user đang dùng app trên 2 điện thoại và đăng xuất ở điện thoại A → cả điện thoại B cũng bị đăng xuất theo, dù họ không có ý định đó. Thêm nữa, đăng nhập bằng Google bị bug vì token luôn mang `tokenVersion = 0`.

**Kết luận:** `tokenVersion` sẽ bị xóa khỏi codebase.

---

### Tại sao không dùng Token Blacklist (danh sách đen)?

Blacklist hoạt động như thế này: khi user đăng xuất, access token được đưa vào một bảng "danh sách cấm". Mỗi request sau đó sẽ kiểm tra xem token có trong danh sách đó không.

Cách này phổ biến trên **web** vì token thường lưu trong `localStorage` — nếu bị tấn công XSS thì kẻ xấu có thể dùng token đó mãi, nên cần thu hồi ngay lập tức.

**Nhưng trên mobile thì khác:**
- Access token lưu trong **RAM** (Provider/Riverpod) → khi đóng app là mất
- Refresh token lưu trong **Android Keystore** → khi gỡ app là tự xóa
- Mỗi thiết bị có **refresh token riêng** trong DB

Khi user bấm "Đăng xuất":
1. App gọi `POST /auth/logout` gửi kèm `refreshToken`
2. Server xóa refresh token đó khỏi DB → thiết bị đó không refresh được nữa
3. App xóa access token và refresh token khỏi bộ nhớ

Kẻ xấu nếu có access token cũ thì chỉ dùng được tối đa 1 tiếng (TTL còn lại), sau đó không refresh được vì refresh token đã bị xóa. **Đây là trade-off chấp nhận được cho mobile.**

**Kết luận:** Không cần blacklist — thêm vào chỉ tốn thêm 1 query DB mỗi request mà không có lợi ích thực tế cho mobile.

---

### Tóm tắt thiết kế token đã chốt

| Thứ | Giá trị | Lý do |
|---|---|---|
| Access token TTL | **1 giờ** | Đủ ngắn để hạn chế rủi ro, đủ dài để không phải refresh liên tục |
| Refresh token TTL | **7 ngày** | Không bắt user đăng nhập lại mỗi tuần |
| Access token lưu ở FE | **RAM** (Provider/Riverpod) | Mất khi đóng app, không persist — an toàn |
| Refresh token lưu ở FE | **flutter_secure_storage** (Android Keystore) | Mã hóa bởi OS, tự xóa khi gỡ app |
| Thu hồi khi logout | **Xóa refresh token khỏi DB** | Đủ để vô hiệu hóa thiết bị đó |
| tokenVersion | **Đã loại bỏ** | Bug googleLogin, logout all devices |
| Token blacklist | **Không dùng** | Không cần thiết cho mobile |

---

### ⚠️ Thay đổi so với plan gốc — FE cần biết

Plan gốc chốt "token 7 ngày, không cần refresh token". **Nhóm đã chốt đổi sang:** access token 1 giờ + refresh token 7 ngày với token rotation.

**FE phải làm thêm:**
- Lưu `refreshToken` vào `flutter_secure_storage` (Android Keystore), không phải RAM
- Khi nhận lỗi `TOKEN_EXPIRED` (401) → tự động gọi `POST /auth/refresh` để lấy cặp token mới
- Nếu `/auth/refresh` cũng thất bại → điều hướng về màn đăng nhập

## Phần 2 — Review nhánh B2 (Auth API)

### Vấn đề 1 — tokenVersion không được đưa vào access token khi refresh

**File:** `server/src/repositories/token.repository.js` — hàm `findRefreshToken`, dòng 13–23

Khi FE gọi `POST /auth/refresh`, server lấy thông tin user từ `findRefreshToken`. Hàm này chỉ trả về các trường trong `clientUserSelect` (id, email, fullName, role, avatarUrl) — không có `tokenVersion`. Sau đó `generateAccessToken(tokenRecord.user)` tạo access token mới với `tokenVersion = 0` (do không tìm thấy field, code trong `utils/token.js` fallback về 0).

**Hành vi:** User đăng xuất → `tokenVersion` trong DB tăng lên 1 → User đăng nhập lại → lấy access token mới (tokenVersion=1) → Gọi `/auth/refresh` → access token mới nhất lại có tokenVersion=0 → Middleware từ chối ngay lập tức với lỗi TOKEN_REVOKED.

**Hướng fix:** Thêm `tokenVersion: true` vào select trong `findRefreshToken`, hoặc loại bỏ hoàn toàn `tokenVersion` như đã thảo luận.

---

### Vấn đề 2 — `deleteUserRefreshTokens` và `sendError` chưa dùng đến

**File:** `server/src/repositories/token.repository.js` dòng 33–37 và `server/src/controllers/response.js` dòng 15–21

Hai hàm `deleteUserRefreshTokens` và `sendError` được export ra nhưng không có chỗ nào trong codebase import và gọi chúng.

**Không gây lỗi runtime** nhưng đây là dead code — người đọc sẽ mất công tìm chỗ dùng.

**Hướng fix:** Xóa nếu không có kế hoạch dùng, hoặc comment lại lý do giữ.

---

## Phần 3 — Review nhánh B3 (Job API)

### Vấn đề 1 — Route recruiter bị nhét nhầm vào `index.js`

**File:** `server/src/index.js` — dòng 22–27

Hiện tại route `/api/v1/recruiter/jobs` được mount trực tiếp trong `index.js` cùng middleware `authenticate` và `authorize`. Nhưng tất cả các route job khác thì nằm trong `job.routes.js`.

**Hành vi:** Khi thêm route job mới mà không để ý thì sẽ có một số route nằm trong `index.js`, số khác trong `job.routes.js` → code loạn, khó bảo trì.

**Hướng fix:** Chuyển route recruiter vào `job.routes.js`, dùng router riêng hoặc prefix riêng trong `index.js`.

---

### Vấn đề 2 — Lọc kỹ năng phân biệt chữ HOA/thường

**File:** `server/src/repositories/job.repository.js` — hàm `buildPublicJobWhere`

Khi FE gửi `?skills=react`, server lọc bằng `hasSome: ["react"]`. Nhưng trong DB nếu job lưu là `"React"` (chữ hoa R) thì sẽ không khớp vì PostgreSQL array `hasSome` phân biệt hoa thường.

**Hành vi:** User tìm job React nhưng app không trả kết quả gì dù DB có data, khiến user nghĩ app bị lỗi.

**Hướng fix:** Normalize skills về lowercase trước khi lưu job. Đồng thời `parseSkills` cũng lowercase đầu vào trước khi query.

---

### Vấn đề 3 — Nuốt lỗi DB trong `getJobDetail`

**File:** `server/src/services/job.service.js` — hàm `getJobDetail`, dòng 133–138

Đoạn `catch (_error)` bắt toàn bộ lỗi và biến thành 404. Kể cả khi DB đang down hoặc mất kết nối cũng sẽ trả về "Không tìm thấy job" thay vì lỗi 500.

**Hành vi:** Server đang có lỗi nghiêm trọng nhưng log không thấy gì, user thấy 404 và tưởng ID sai → khó debug khi deploy.

**Hướng fix:** Chỉ catch lỗi Prisma liên quan đến sai định dạng ID (`PrismaClientKnownRequestError` với code `P2023`). Các lỗi khác để throw lên cho `errorHandler` xử lý.

---

### Vấn đề 4 — Response trả về field trùng lặp

**File:** `server/src/services/job.service.js` — hàm `getPublicJobs` và `getRecruiterJobs`

Mỗi job trong response hiện có 3 field cùng giá trị:
```json
{
  "applicationsCount": 5,
  "totalApplications": 5,
  "_count": { "applications": 5 }
}
```

Và `meta` cũng có 2 field tổng số: `"total": 100, "totalItems": 100`.

**Hành vi:** FE đọc code không biết nên dùng field nào, dễ bị inconsistent giữa các màn hình.

**Hướng fix:** Chốt 1 field duy nhất. Đề xuất giữ `applicationsCount` và `total` trong meta.
